### Vanilla (1.21.11, Mojang names; read ~/Desktop/null-reference/vanilla-1.21.11-src/net/minecraft/ to confirm)

Describe vanilla in your own words in comments. Never copy Mojang, Paper or Grim code.

Who pushes the bot, and when:
- The bot is the local player. `LivingEntity#pushEntities` (`world/entity/LivingEntity.java` ~3072) runs at the end of every living entity's `aiStep` on the client. It asks `Level#getPushableEntities`. On the client, `ClientLevel#getPushableEntities` (`client/multiplayer/ClientLevel.java` ~432) returns only the local player, and only when it is not the caller and its box intersects the caller's box (strict test). So the local player is never pushed by its own call. Nothing else is pushed on the client.
- `EntitySelector#pushableBy` (`world/entity/EntitySelector.java` ~27) decides. On the client it accepts only the local player as target. It also rejects a target that fails `isPushable` or is a spectator.
- `LivingEntity#isPushable` (~3211): the target is alive, not a spectator, and not on a climbable block. `Entity#push(Entity)` (`world/entity/Entity.java` ~1744) adds two checks: the target has no passengers, and neither entity has `noPhysics`. `LivingEntity#push(Entity)` (~2224) adds: a sleeping target is not pushed. This one applies to pushes by living entities and remote players only. A boat calls `Entity#push` through `AbstractBoat#push`, which has no sleeping check.
- The math (`Entity#push(Entity)`): take the horizontal offset from the bot to the pusher. Let f be the larger absolute axis. If f < 0.01 (a float constant), nothing happens. Otherwise divide both axes by sqrt(f), then multiply both by min(1, 1/sqrt(f)), then by 0.05 (float constant). Add the result to the bot's velocity with the sign away from the pusher. Vertical push is 0. Worked check: for f < 1 the larger axis gets 0.05 × sqrt(f); for f ≥ 1 it gets exactly 0.05. Offset 0.3 gives 0.0274. Use the float constants widened to double (`0.05f32 as f64`, `0.01f32 as f64`), as patch 30's model does for 0.98.
- The pusher also changes its own client velocity in the same call (when it has no passengers and is pushable). Nothing in the fork reads a remote entity's velocity, so skip it. Write that down in a comment.
- Pusher types:
  - Every living entity (mob, remote player) pushes, with its own box. The pusher's own health and pushability are not checked: a dying mob (until the server removes it, up to 20 ticks) and a ridden horse still push. (This corrects PATCH_30_TIER1 §2.3, which listed the ridden horse as an exception. `AbstractHorse#isPushable` is only about being a target.)
  - Exceptions: `ArmorStand` pushes no player (`ArmorStand#doPush` is empty; its `pushEntities` only touches ridable minecarts). `Bat` pushes nothing (`Bat#doPush` and `pushEntities` are empty). `Parrot#doPush` skips players. A pusher with `noPhysics` is skipped by `Entity#push`: a spectator remote player (`Player#tick` sets it from the game mode), a Vex (`Vex#tick` sets it around `super.tick()`, so its `aiStep` sees it), an Ender Dragon (set in its constructor). The shulker pushes like any living entity; its empty `Shulker#push(Entity)` is the target side and does not matter here.
  - `AbstractBoat#tick` (`world/entity/vehicle/boat/AbstractBoat.java` ~272) pushes with a box inflated 0.2F sideways and −0.01F vertically (float constants widened). It skips a bot that has the boat as passenger. Its `push` override (~175) adds a height rule that PATCH_30_TIER1 §2.3 does not list: the bot is pushed only when the bot's box bottom is at or below the boat's box bottom (a bot above the boat's bottom is not pushed). It pushes by distance too: no overlap is needed, a gap under 0.2 is enough.
  - Minecarts do not push on the client: `AbstractMinecart#push` (~483) and both `pushAndPickupEntities` paths run on the server only. Non-living entities (items, arrows, item frames, projectiles) never push.
  - `Entity#isPushedByFluid` (`Entity.java` ~3164) is the fluid push. It is out of scope.
- Position and box used: the pusher's box after its own interpolation step in this tick. The bot's box is the one at the time of the push (see the tick order below).
- Velocity packets: `ClientPacketListener#handleSetEntityMotion` (~621) replaces the velocity at once (`Entity#lerpMotion`, ~2529). The packet is applied before the tick, so a push from the tick before is overwritten by it. Same for knockback. Nothing special to build; keep the order.
- Cramming damage is server-only. Skip it. When the server freezes ticks, `TickRateManager#isEntityFrozen` (`world/TickRateManager.java` ~63) stops every non-player entity, so mobs and boats stop pushing; remote players still tick. The fork has no frozen-entity state (`tick_clock.rs` notes the gap). Do not use `/tick freeze` in rows, and list the gap in your report.
- The server never tells the bot about a push. `ServerEntity#sendChanges` (`server/level/ServerEntity.java` ~167) sends a push-caused velocity change to tracking players, not to the player itself. So the bot computes pushes alone, and the server sees only the resulting positions.

Teams:
- `Entity#getTeam` (`Entity.java` ~2653) looks up the entity's scoreboard name in the client scoreboard. `Entity#getScoreboardName` (~3160) is the UUID as text for every entity except players. `Player#getScoreboardName` (`world/entity/player/Player.java` ~1693) is the profile name. So mobs and boats are keyed by UUID text, players (bots included) by name.
- `ClientPacketListener#handleSetPlayerTeamPacket` (~2272), in words: Add creates the team (an existing name is reused); any other action on an unknown team is ignored with a warning. If the packet has parameters (Add and Change), set the collision rule and the rest. Then the member action: Join adds each name (the `Scoreboard#addPlayerToTeam` call first removes the name from its old team, `world/scores/Scoreboard.java` ~279); Leave removes each name (vanilla throws when the name is on another team; the fork ignores it and logs). Remove drops the team and clears all its members.
- The rule (`EntitySelector#pushableBy`, ~27 to ~50), for pusher team A and bot team B, with no team counting as `always`. If A is `never`: no push. If B is `never`: no push. `allied` means both have the same team (`Team#isAlliedTo` compares identity; a missing team is never allied). If either is `pushOwnTeam` and allied: no push. Otherwise: push when neither is `pushOtherTeams`, or when allied. Grim holds the same table (`EntityPredicates#canBePushedBy`, `grimac/common/.../utils/team/EntityPredicates.java`). Write a table test of all 4 × 4 × 2 cases from this text, not from the fork code.
- Paper (`collisions.enable-player-collisions`, default true, also true in `harness/grim-server`) can send `never` in team packets and filter players. Default settings change nothing. The team store handles that case with no extra code.

Tick order:
- `ClientLevel#tickEntities` (`ClientLevel.java` ~347) walks `EntityTickList` (`world/level/entity/EntityTickList.java`): a map keyed by entity id that keeps insertion order. `tickNonPassenger` (~364) ticks an entity, then its passengers at once; the main loop skips passengers. Bots do not ride (a passenger bot is a `Movement` entry and disconnects), but mobs can.
- An entity joins the list when it is added to the level and its chunk section is ticking (`TransientEntitySectionManager#addEntity` ~55, callbacks in `ClientLevel` ~1122). It leaves on removal. Removing and adding again puts it at the end. The fork does not model the chunk-section ticking state. List that as a gap: an entity in a chunk that loads later ticks later in vanilla.
- The local player is one entry. At login it is added first (`handleLogin`), so it ticks before every entity that arrives later. A respawn in the same dimension builds a new player with the same id and calls `ClientLevel#addEntity` (~418), which removes the old entry first: the bot moves to the end of the order (`ClientPacketListener#handleRespawn` ~1259 to ~1335). A respawn into another dimension builds a new `ClientLevel` with an empty list (~1275), so the bot is first again.
- Where the push lands: an entity that ticks before the bot pushes the bot before the bot's `tick`, so this tick's `aiStep` (velocity floor, travel) uses it. The bot's box is the one from the end of the last tick. An entity that ticks after the bot pushes after the bot's whole tick, including `sendPosition`, with the bot's new box; the push changes the next tick's travel. `LocalPlayer#tick` (`client/player/LocalPlayer.java` ~225) sends the position inside the bot's own tick.
- The bot's own `aiStep` zeroes a player's horizontal speed under 0.003 (square under 9.0E-6) near its start (`LivingEntity#aiStep` ~2880), so a push must land before this step to count in the same tick. The fork's `ai_step` already does this.

### Grim (name the check in doc comments)

- `MovementTicker#handleEntityCollisions` (`grimac/common/.../predictionengine/movementtick/MovementTicker.java` ~47) counts, each tick, the entities whose possible box meets the bot's box (last to new position, widened by 0.2) that are pushable by type (`TypedPacketEntity#isPushable`: living, boats and minecarts; not armor stands, bats, parrots) and that pass the team table. It keeps the counts of the last 3 ticks (`UncertaintyHandler.collidingEntities`) and `PredictionEngine#handleStartingVelocityUncertainty` (~490, ~540) widens the horizontal tolerance by 0.08 per counted entity. Grim does not compute the push, the direction, the order or the interpolation. So Grim stays quiet for a small error, and it cannot prove that a push is exact. The exact check is the independent model in your rows. A bot that ignores pushes accumulates drift over many ticks and can draw a `Simulation` alert.
- Grim keys teams like vanilla (`TeamHandler`: UUID text for entities, name for players). It counts minecarts although the client does not push from them; that only widens the tolerance.
