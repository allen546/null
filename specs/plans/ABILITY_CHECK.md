# Ability check: what the bots can do, proven live

**Plan, 2026-10-17 (Allen).** A milestone between S4 and S5 in [BUILD_PLAN.md](BUILD_PLAN.md). Before any skill is built on top, confirm that the basic abilities exist and act correctly on a real server. Where Azalea is missing one or gets it wrong, patch the fork ([reference/AZALEA_PATCHES.md](../reference/AZALEA_PATCHES.md)) or add it in `mc-adapter`. The duel already found four Azalea bugs by accident; this looks for the rest on purpose.

The starting picture is the Azalea reality check ([reference/AZALEA_REALITY_CHECK.md](../reference/AZALEA_REALITY_CHECK.md) §3): mining, inventory clicks, respawn are covered; placing is partial; item use (eating, shields, bows) and crafting helpers are missing; attackers are not tracked.

## The bar

An ability passes only when the **server** confirms it, not the bot's own view:
- read back through RCON (`data get entity`, `data get block`, `execute if block`, `clear <bot> <item> 0` to count items);
- no anticheat or movement warnings in the server log ("moved too quickly", "moved wrongly", kicks);
- **zero GrimAC alerts.** Null targets vanilla servers, and the fork and adapter must also run cleanly on Paper with an anticheat (F5 §4.6, Allen, 2026-10-17). So a scenario passes only when it passes on both: vanilla `harness/skeleton-server` (the target) and Paper + Grim `harness/grim-server` (the strict check, timing included, zero alerts). Behaviour identical to vanilla means identical Grim alerts (Allen, 2026-10-23): a row may allow an alert only when a trace proves a vanilla client would draw it too (`Ctx::run_allowing`, listed in F5 §4.6: AT's forced stall, A23's resync loop); A bot never sends a click a vanilla client could not make: it refuses on the client, with a reason, and sends nothing;
- vanilla timing: eating takes 32 ticks, a break takes the vanilla time for the tool. Timings a server can change are beliefs, not facts (Allen, 2026-10-17): the shield's raise-to-block delay is the held item's `blocks_attacks.block_delay_seconds` (0.25 s = 5 ticks by default), and plugins or older Paper settings can change it, so A6 measures the server's delay and checks the bot's belief against it.

Each ability is a scripted scenario: RCON sets the scene (give items, place blocks, set food), one bot does the thing, RCON checks the result. The runner prints one pass or fail line per scenario with the evidence, so a verifier can rerun it. A failure becomes a fix in the fork (raw capability) or the adapter (translation only, F5 §4.1), then a rerun.

## Tasks (Sonnet implements, 500–800 lines each; Haiku or Sonnet verifies live)

1. **Runner, slots, breaking, pickup, placing (A1–A4).** A `null-abilitycheck` binary: connects one bot through `mc-adapter`, talks RCON to `skeleton-server` (port 25577), runs scenarios by name, prints pass or fail with evidence. Adds `break_block`, `place_block(pos, face)` and the inventory view to `null-bot-api` and `mc-adapter`.
2. **Item use and attackers (A5–A8).** Hold and release with the real duration (`using_item` reports the hand and ticks); eating; shield; attack checks; `recent_attackers` from the damage event and the hurt packet's source (likely a fork patch).
3. **Inventory, containers, crafting (A9–A11).** Click actions, `open_container`, container contents in the view, crafting by clicks without the recipe book. A10E follows A10: aiming at an entity's hitbox and the entity interact packets as a vanilla client sends them (Azalea's port of `getEntityHitResult` exists; nothing aims or checks an entity click yet), then the same container rows on minecarts and a chest boat. Menus that do work (furnaces, anvil, enchanting, brewing, trading and the rest) come with their skills; their result slots are computed by the server, so their rows allow corrections there only.
4. **Respawn (A12)**, then the whole suite run live by a separate verifier; failures go back as fixes.

Every new function carries its `// Spec:` link. Every fork change is one commit on `null-main` with a row in AZALEA_PATCHES.md, and `Cargo.toml`'s pinned `rev` moves to it.

## Which modules a change reruns (Allen, 2026-10-21)

A change reruns only the modules it affects, once per server. Agents run these selective runs themselves. The full pair (`--scenario all` on both servers) runs once per fork push, not per patch; Allen runs it offline (`scripts/full_suite.sh <prefix>`). The full pair stays as the gate because a fork change can reach rows that no map names, and because load effects show only in long runs.

- A harness change inside one module reruns that module.
- A change to shared harness code (`scenarios.rs` `Ctx`, `rcon.rs`, `skill.rs`, `main.rs`) reruns the modules that call the changed function.
- A Null change (`null-bot-api`, `mc-adapter`, `null-skills`, `null-node`) and a fork change rerun the modules that the map below lists for each changed area, plus the modules with new or changed rows.
- Selective runs are sound only when each module sets every piece of server state it relies on: spawn point, game rules, effects, attributes, gamemode, held items, time and weather. A row that passes alone but fails after other modules (or the reverse) is an isolation bug, and it is fixed in that module.

The map (Null or fork area to modules) is the file `crates/null-abilitycheck/run_map.toml`; `scripts/affected_modules.sh` reads it (below). It was built by tracing each module's `Op`s through `skill*.rs` to the `null-bot-api` and `mc-adapter` calls and on to the fork systems they reach. It is coarse: one entry per crate area or file; the longest matching path prefix decides. Summary:

- **Every module (`all = true`):** the tick loop, connection, login and packet handlers (`azalea-client` by default, including `movement.rs`, `inventory/`, `packet/`, `tick_*`, the unmodelled gate), `azalea-protocol/-core/-world/-registry`, `azalea-entity` by default (attributes, effects, `unmodelled.rs`; `scene_in` gives every module effects, attributes and `SelectSlot`), `azalea-block` and `azalea-inventory` by default, the runner crate `azalea`, `null-bot-api`, `mc-adapter`, the shared harness (`main.rs`, `rcon.rs`, `skill.rs`, `scenarios.rs`), the `Cargo` files and `harness/` (server settings).
- **Blocks:** `block_actions.rs` and `interact/` (the crosshair ray) reach the modules with a break, place, open-container or gather op: A1 A2 A2S A3 A4 A4C A4S A10 A10E A11 A12 A13 A14 A16 AT (`interact/` adds A5-A8: item use and attack). `mining.rs` (client and entity): A1 A2 A2S A3 A12 A13 A14 A16. `click_use.rs`: A1 A4 A4C A4S A10 A10E A11 A12 A13 AT.
- **Movement:** the physics core (`azalea-physics` `lib.rs`, `travel.rs`, `client_movement.rs`, `collision/mod.rs`, `world_collisions.rs`) reaches every module that walks, jumps, falls or crouches: A2S A3 A4C A4S A5-A8 A10 A10E A12 A14 A15 A16 A17 AT (A1, A2, A4, A9, A11, A13 only stand). Shapes and the ray (`collision/blocks.rs`, `shape.rs`, `clip.rs`) reach the aim modules. `unmodelled_contacts.rs`: A15 A16 A17. The pathfinder: A3 A12 A14 A15 AT.
- **Items and entities:** `item_use.rs`: A5-A8 A12. `attack.rs`, `attackers.rs`: A6-A8. `entity_actions.rs`: A10E A12. `respawn.rs`: A12 A17. `entity_collisions.rs`: A7 A8 A10E A12 A17. Window clicks (`azalea-inventory` `operations.rs`): A9 A10 A10E A11 A12.
- **Null crates:** `null-skills`, `null-belief`: A14. `null-combat`, `null-mechanics`: A5-A8. `null-node` and `null-skills-demo`: none. A harness file for one module maps to that module; `skill_items.rs` to A5-A8 A12 A15-A17, `skill_inventory.rs` to A4C A9-A12, `skill_respawn.rs` to A12 A17.
- **No effect on a run (`ignore`):** specs, scripts, markdown, logs, fork tests and codegen. A path that matches nothing makes the helper print `all` and name the path.

The history check (`scripts/affected_modules.sh --check-history`) takes the files of each fork patch 20 to 30 from the fork's git log and checks that the map's set contains the modules the patch's tests named (`[[history]]` in the map). Because `packet/game/mod.rs` and most of `azalea-entity` are `all`, patches 20-24 and 26-27 and 30 come out as `all`; patches 25, 28 and 29 come out narrow (A1 A2 A2S A3 A4 A4C A4S A10 A10E A11 A12 A13 A14 A16 AT, and A5-A8 for 29). No patch misses a module. A new fork patch adds a `[[history]]` entry with the modules its rows name.

Helper: `scripts/affected_modules.sh [--fork-rev <rev>] [--explain]` reads `git diff --name-only HEAD` plus untracked files of the Null tree and of the fork (against the `rev` pinned in `Cargo.toml`, or `--fork-rev`), and prints one argument: `--scenario A5,A6,...`, `--scenario all` or `--scenario none`. `--explain` prints the reason for each path on stderr.

**Isolation (2026-10-21).** `Ctx::scene_in` calls `reset_player` before every scene: gamemode survival, `effect clear`, `base reset` of 20 attributes (A16 and A17 set movement_speed, sneaking_speed, jump_strength, gravity, step_height, scale, block_break_speed, max_health, armor), `modifier remove` of the two modifiers the suite adds (`a16_slow`, `a16_fast`), the three game rules some module changes (`keep_inventory false`, `immediate_respawn false`, `natural_health_regeneration true`), `difficulty normal`, the spawn point at the area's centre, full health and food, and a wait (up to 8 s) until fire and frost are gone. The scene also kills every non-player entity in the area, puts the bot back in the overworld, and clears the inventory and the held slot as before. No row sets time or weather (both servers keep time fixed and weather clear). Isolation bugs found and fixed in modules: A6 set `natural_health_regeneration false` once before its damage rows and each row's `scene` now resets it, so each row sets it again; A12 `fresh` kills item entities within 60 blocks (the drop search reaches 48, past the module's area); A17 `control_free_fall` skips the trace ticks before the teleport arrives (RCON answers before the bot sees it), and the Slow Falling arrow row compares the first four ticks with the effect by what the tick did to the move (the hit's motion packet lands in any of them). `scene_in` teleports first and resets after, because the last module's cleanup can remove the floor and the chunks under the bot (a fall there drew a Grim `Simulation` alert). `--shuffle <seed>` runs the chosen modules in a random order from the seed (rows inside a module keep theirs) and prints the seed and the order on the summary line.

### How to run

```
harness/grim-server/scripts/start_server.sh       # wait for "RCON running" in its server/server.log
harness/skeleton-server/scripts/start_server.sh   # the vanilla server, same
cargo build --release -p null-abilitycheck
./target/release/null-abilitycheck --server 127.0.0.1:25568 --rcon-port 25578 \
  --server-log harness/grim-server/server/server.log --account null_check --scenario all
./target/release/null-abilitycheck --server 127.0.0.1:25567 --rcon-port 25577 \
  --server-log harness/skeleton-server/server/server.log --account null_check --scenario all
harness/grim-server/scripts/stop_server.sh; harness/skeleton-server/scripts/stop_server.sh
```

A scenario passes only when it passes on both servers (F5 §4.6). The two runs can go at the same time (separate servers, worlds and logs); each takes about 10 minutes. Rows print as they finish; if the bot stops answering, the runner prints a `RUN <module>_aborted` FAIL row and stops.

`--scenario A1,A5,...` runs a subset (`--shuffle <seed>` in a random module order, for a full pair: `scripts/full_suite.sh <prefix> --shuffle <seed>`); `SHAPES_ONLY=<text>` reruns the shape rows whose name contains the text. Several runs can share the server with different `--account` names (the log check skips other `null_` accounts) as long as each scenario module uses its own test area (`Ctx::scene_in`).

Timing: every PASS/FAIL line ends with ` [N.N s]` (the row's wall time). After the summary line the runner prints `TIMING` lines: total, time per module (setup and cleanup included) slowest first, the 10 slowest rows, and the time spent waiting for RCON replies. Fixed sleeps are not summed (about 150 call sites). `scripts/full_suite.sh <prefix>` runs both servers in one command (HANDOFF "How to run"). **Warm-up gate (2026-10-21):** every `scene_in` ends with `Ctx::settle_server`, which waits until the server's mean tick time over its last 100 ticks (`tick query`) is under 15 ms, at most 30 s. A slow server (the Pi in its first 30 s, chunk loads after a teleport) otherwise makes RCON readbacks late: the Pi pilot failed three A2 break-time rows that way while the bot's own timing was exact. On the Mac it returns at once. A wait over 1 s is printed to stderr; a server that never settles is reported, and the run goes on.
