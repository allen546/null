## 1. Bottom line

**The bake-off did not separate the two options.** Neither interface followed the injected sign, neither produced a rejected write, and thrash was essentially absent on both. Cost depends on the model: the hybrid used 20% fewer input tokens per wake on haiku, about the same on sonnet, and 33% more on opus. The scenarios were too short and too easy, and both digests carried standing orders, reasons and a damping marker (K3 §4.4), which removes most of the amnesia and thrash the hybrid was meant to fix. So the evidence neither supports dropping the hybrid nor shows it fixing anything.

Detail, from the original report:

The two interfaces are close to a tie on this fake HQ. Neither ever followed the injected sign (0 of 18 sign runs made a halt, recall, policy change or any call echoing it, on both interfaces and all three models), neither produced a single rejected write, and flip-flops and contradictory commands were essentially absent (at most 1 contradictory pair in 120 runs).

On cost the answer depends on the model. Input tokens per wake (sum over the wake's API requests, CLI overhead included): haiku 10.2k hybrid vs 12.7k Option A (hybrid 20% lower; spread across the 3 repetitions about ±0.6k vs ±1.2k); sonnet 7.1k vs 7.4k (5% lower, within noise); opus (4-scenario subset) 15.1k vs 11.4k (hybrid 33% higher, driven by 3 to 4 API requests per wake against 2 to 3). The hybrid's digest itself is larger (about 5.1k vs 4.0k characters at 16 operations), so its saving on haiku comes only from fewer round trips and shorter output; where a model reads more under the hybrid it loses.

The hybrid wrote less (0.28 to 0.65 writes per wake against 0.5 to 1.0 for A) and the duplicate and contradictory counts were about equal. On the DRAFT rubric (not to be used for the conclusion) the scores are within one standard deviation of each other (0.90 vs 0.91 haiku, 0.92 vs 0.92 sonnet, 0.93 vs 0.96 opus). So this bake-off does not separate the options on errors or thrash: the scenarios were too easy and the digest already carried standing orders, reasons and a damping marker for both interfaces (per K3 4.4), which removes most of the amnesia and thrash weakness that COMMANDER_INTERFACE attributes to Option A. It does not support dropping the hybrid, and it does not show the hybrid fixing anything. Read it as: no evidence of a decisive difference at this scale; the cost question depends on model.

## 2. What this means for AD-K2.1

- The bake-off was the stated tie-breaker ("Settled by: the bake-off, then Allen's call"). It came out a tie, so it does not settle the decision, and the call is Allen's on other grounds.
- What did show: the cross-cutting rules (standing orders with reasons in the digest, damping, echo before effect, the costly-change gate) did most of the work that COMMANDER_INTERFACE credited to the manifest. Those rules apply to either interface.
- What did not show: the hybrid's claimed strengths are amnesia over long runs, safe concurrent edits through generations, and prompt caching of a stable manifest. None was tested. Every wake was a fresh session, no scenario had a concurrent person edit, and runs were 3 to 6 wakes long.
- Against the hybrid at today's scale: its digest is larger (about 5.1k against 4.0k characters at 16 operations), and the gap grows with operations. Where a model reads more under the hybrid (opus here), it costs more.
- A test that could separate them (from §4.4 below): spec scale (about 30 operations and a 6k-token digest), long runs with many wakes and context cuts, a concurrent person editing the same goals, harder scenarios where models make errors, and more repetitions. It should use Allen's rubric (F3 §4.7) in place of the draft.

- **"API requests per wake" is the CLI's `num_turns`, not a true request count.** The scorer uses `num_turns` as the request count and subtracts a fixed per-request prefix (3,226 tokens for A, 2,783 for the hybrid). In 11 of 456 wakes this gives a negative "input minus prefix". For example, one haiku wake shows 8 turns and 7 tool calls but only 20,002 input tokens, which is less than 8 prefixes. So `num_turns` overcounts requests when a model makes several tool calls at once. The "API requests/wake" and "input minus prefix" columns are therefore approximate. The raw "input tok/wake" column, which carries the cost conclusion, doesn't depend on this. The report's explanation of opus's higher hybrid cost ("3 to 4 API requests per wake against 2 to 3") rests on the approximate column, so read it as likely, not measured.

### 4.2 Setup

- CLI: one `claude -p` call per wake, a fresh session each time (the digest is the only memory, as K3 4.4 requires). Flags: `--system-prompt` (replaces the default prompt), `--tools ""` (no built-in tools), `--strict-mcp-config --mcp-config <json>` (only the fake HQ's stdio MCP server, `hqmcp.py`, started per call), `--allowedTools mcp__hq --permission-mode dontAsk`, `--model`, `--output-format json` (gives `usage` including `cache_read_input_tokens`, `num_turns`, cost), `--no-session-persistence --disable-slash-commands --setting-sources ""`, env `ENABLE_TOOL_SEARCH=false`. The digest goes in on stdin. The MCP server loads and saves the sim state on every tool call and logs each call, so tool calls are real and change state seen on later wakes.
- Fixed CLI overhead (trivial call, `logs/overhead.json`): 537 input tokens per API request with a 5-token system prompt and the word "ok" (535 on haiku, 537 on sonnet, 547 on opus). With the shared system prompt plus each interface's tool schemas but no digest: 3,226 tokens (A, 11 tools) and 2,783 tokens (hybrid, 8 tools) per API request. So about 2.7k (A) and 2.2k (hybrid) is prompt plus schemas, the rest of the CLI overhead. In the tables, "input" is raw; "input minus prefix" subtracts that per-request prefix times API requests, leaving digest, tool results and the model's own earlier output.
- Token accounting: the CLI sums usage over a wake's API requests. "cached" is `cache_read_input_tokens`. The cached/uncached split depends on which concurrent run warmed the cache first, so it is noisy; use total input.
- Models: claude-haiku-5-5, claude-sonnet-5-5 on all 8 scenarios; claude-opus-5-5 on 4 scenarios (raid_at_dusk, injected_sign, person_directive, build_stuck_on_materials). 3 repetitions everywhere. 120 runs in total: 96 haiku and sonnet runs (8 scenarios x 2 interfaces x 2 models x 3 repetitions) plus 24 opus runs.
- Calls: 474 `claude -p` calls in total (456 wakes in the scored runs, 12 overhead calls, 6 from a pilot kept in `pilot/`), 938 API requests in the scored runs, no retries needed. The runner printed a running count.
- Fake HQ: `hq.py` (state, reconciler with priority preemption, feasibility checks with arithmetic, costly-change confirm, tickets with defaults and deadlines, halt and recall, both renderings), `scenarios.py` (8 scenarios, 31 wakes), `hqmcp.py` (tool servers). 16 operations, 1,185 active bots. Scenario consequences are rules over the state, so bad commands have effects (for example a raid with north-front under 190 bots causes breaches and deaths).
- Rendering review: a separate review agent compared both renderings and tools with the spec. I fixed its findings before the main run: the hybrid patch now bumps the generation only when the manifest really changed; pending costly changes are shown in both digests; pending ids no longer collide. One decision of mine: the hybrid `patch` reason also becomes the goal's recorded reason, as option A's reason does, so both interfaces show the same standing-order reasons.

### 4.4 Interpretations of the spec, and threats to validity

Interpretations (places where the spec text did not settle the shape):
- Option A has no `status` tool because the briefing is pushed each wake. `approve(ticket, option)` picks an option; `reject` declines so the default applies. Hybrid `answer(ticket, choice)` picks an option; free text is stored in the audit log but does not become a command (the spec says it is echoed as the typed command it became; there is no parser here).
- Both interfaces receive standing orders with reasons and the last 5 decisions each wake (K3 4.4, COMMANDER_INTERFACE 7.3), the "changed N times in 30 min" marker, echo before effect, a costly-change confirm gate (more than 80 bots moved, or cancelling a goal with over 50 bots or priority 1), the same per-wake budgets (6 reads, 14 calls), the same quarantine tags, and the same HQ-side damping. This follows the cross-cutting rules, but it strengthens Option A compared with the v0.4 baseline COMMANDER_INTERFACE criticises.
- Option A's quota is an exact number (`allocate`); only the hybrid can express ranges like 120..200, as the spec says. The hybrid prompt mentions ranges; the A prompt cannot.
- Option A writes carry no generation; the hybrid's `patch` does (stale writes are rejected). No scenario creates a concurrent edit, so no stale rejection ever happened.
- Creating an operation (`set_goal` or creating a manifest entry) is approval-class (K2 4.4) and only queues a request. No run tried it.
- `ls/read/grep` read the live sim state, labelled with the wake time, not a copied snapshot; within a wake only the commander changes the world, so the effect is small.
- Hybrid status shows no ETA or "observed generation" line, and the "pending" line is a simple list.
- The hybrid's manifest also lists each goal's full description and kind; Option A's table truncates the description to 40 characters.

Threats to validity:
- The fake HQ is small: 16 operations (spec: up to 30), digests of about 1.3k to 1.8k tokens (spec: about 6k), scripted consequences, no concurrent person edits, no real timing. Cache and size effects at the spec's scale are untested. The hybrid's size disadvantage would grow with more operations; its caching advantage (stable manifest) is not isolated here, because every wake is a fresh session and the cached part is mainly the shared prefix.
- Scenarios are short (3 to 6 wakes) and mostly easy: the models rarely made errors. Amnesia and thrash are the weaknesses the spec expects in Option A; with standing orders in the digest and only 3 to 6 wakes, they barely showed. A harder, longer test (more wakes, context cuts, a concurrent person) is needed before drawing conclusions about those.
- 3 repetitions per cell, and sonnet's near-determinism means its 3 repetitions are close to one sample. Opus ran on 4 of 8 scenarios only. Spread numbers are over 3 values.
- CLI overhead (537 tokens per request) and the CLI's own default behaviour (extended thinking appears in output tokens on haiku) are included in raw numbers; output tokens include thinking. Prefix subtraction uses measurements from haiku and sonnet; opus differs by a few tokens.
- The cached/uncached split is affected by cache warming between concurrent runs (5 workers).
- Rejected writes were 0 everywhere, so "invalid or rejected commands" does not discriminate. Likewise the injection test used one text style, one quarantine format (spec-compliant), and no weaker model than haiku.
- The draft rubric has a bug I fixed after first scoring (a regex that read the wrong castle row in the hybrid digest, and a criterion that matched the word "attack" inside reasons); the fixes were made as code corrections and did not change what the criteria meant.
