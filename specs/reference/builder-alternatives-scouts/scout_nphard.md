# Scout report: NP-hard and PSPACE-hard sequencing and planning

Scope: classical planning, SAT/CP scheduling, pebbling, graph decompositions, MAPF, search methods, and learned heuristics, mapped onto the Minecraft builder problem (problem.md). About 25 searches and 20 fetches. Many search hits returned only link lists, so most claims below come from abstracts or the first ~100k characters of papers. Items marked "unverified" are my inference or from memory without a fetched source.

## Ideas

### 1. Simulator as oracle with lazy nogood learning (CEGAR / CBS / lazy clause generation)

**Idea.** Keep a SAT or CP-SAT model whose variables are pairwise order literals between dependent placements (and optionally bot-assignment literals). Ask the solver for a complete order. Run the offline simulator once on that order. If it fails, extract a small failing core (the pair or short sequence whose relative order caused the unintended change) and add a clause forbidding that pattern. Re-solve. Repeat until a clean order is found, then certify.

**Sources.** Surynek's CEGAR-SAT for MAPF (arXiv 2301.08687) starts from an abstraction that ignores collisions and adds refinements only where failures occur. The paper also leaves some abstractions unrefined on purpose; the SAT answers then need post-processing, and the encodings come out about an order of magnitude smaller. Conflict-based search (Sharon et al., CBS, https://www.cs.du.edu/~sturtevant/papers/sharon2012cbs.html) does the same at the multi-agent level: a high-level tree branches on each conflict as "A before B" or "B before A", with a low-level search per agent; the paper reports up to an order-of-magnitude speedup. Lazy clause generation (Schutt, Feydy, Stuckey, Wallace, arXiv 1009.0347) does it inside the solver: each propagator explains its deductions as clauses, conflicts give first-UIP nogoods, and the solver backjumps. On RCPSP/max with PSPLIB sets it closed 573 of 631 open instances.

**Mapping.** Attacks the redstone-ordering case (the failure core is exactly a forbidden order of dependent placements), the memory case (a bad order is learned once and never retried), and the multi-bot case (CBS-style branching on bot conflicts). Repeated modules in a schematic produce the same failure core, so a nogood learned in one copy blocks the same mistake in every other copy. This is the strongest form of "learn nogoods instead of retrying" the owner asked about.

**Estimate.** Changes the cost from "one simulator trial per candidate action, thousands of trials" to "one simulator run per distinct failure pattern, plus solver time." If failure patterns are few, the simulator call count could fall by one or more orders of magnitude. Unverified for Minecraft. Two risks. First, cores from the simulator are not automatically minimal, and non-minimal cores over-constrain. Second, a memory state may depend on three or more placements at once, so pairwise order literals may be too weak; then the model needs higher-arity order constraints, which is more expensive.

### 2. Cut the cycles and search only the cyclic core (strongly connected components plus feedback arc set)

**Idea.** Build a dependency digraph: edge u to v if the state or placement of u can change the outcome at v. Static rules or a cheap simulator can supply it. Compute strongly connected components (SCCs). The acyclic part of the graph gets a topological order and needs little or no search. Only the SCCs (feedback loops) need search. Inside a cyclic SCC, a minimum feedback arc set chooses which dependency edges to break. Those broken edges are the arming links, and this formalizes "build cold, arm last."

**Sources.** Standard graph theory (minimum feedback arc set is NP-hard; good ILP and heuristic methods exist; unverified citation details here). Planning analogue: Backstrom, Jonsson and Ordyniak (IJCAI 2018, https://www.ijcai.org/proceedings/2018/0647.pdf) show that cost-optimal planning on acyclic causal graphs is polynomial when domain size and up-depth are bounded, FPT in down-depth, and W[1]-hard in up-depth. Treedepth lower-bounds both parameters. The result says tree-like dependency structure is what makes ordering tractable, and cycles are where the difficulty lives.

**Mapping.** Attacks the redstone-ordering case directly. Most of a typical build (walls, floors, support columns, dry paths) is acyclic, so it is ordered by topological sort. Only feedback loops (clocks, latches, repeater rings, piston loops) need search. The cyclic core is the place where the search lives.

**Estimate.** Could cut search size from the whole schematic to a few small SCCs. The gain depends on how big the cyclic cores are. Unverified; a dense redstone build may have one large SCC. Caveat on "arm last": the arming set is not free. Once the feedback arcs are cut, the arming phase has its own ordering problem, and the arming of a loop must happen in an order that does not fire it early. Also, a static dependency graph may miss edges that only appear in certain states (dynamic edges). So the graph should be built conservatively, and the simulator should add edges when it sees an unexpected change.

### 3. HTN-style module decomposition with automated causal failure repair

**Idea.** Write the schematic as a task hierarchy: structure, then modules (a piston door, a clock, a rail line, an entity lock), then primitive placements. Each module has preconditions and an invariant ("after this module, cells X are in state S and nothing else changed"). A failure is localized to the minimal failed subtree by causal-link analysis, the executed prefix is frozen, and planning backjumps to the failed task. This replaces an LLM reading a stuck report with an automatic repair.

**Sources.** Comparison of three HTN plan repair methods (arXiv 2504.16209, https://arxiv.org/html/2504.16209v1): REWRITE (Holler et al. 2020) reproduces the executed prefix exactly and re-derives the rest; it reliably proves unsolvability but is usually slowest. SHOPFIXER (Goldman, Kuter, Freedman 2020) uses causal-link and decomposition analysis to find the minimal failed subtree; it was the most successful on the Rovers domain and scaled best on harder problems, at a bookkeeping cost. IPyHOPPER (Zaidins, Roberts, Nau 2023) restarts at the task that produced the failed action and backtracks only when needed; it has minimal overhead and was fastest on simple problems, but its failures were mostly timeouts on large search spaces. No method dominated.

**Mapping.** Attacks stuck-report debugging (replaces the LLM with a structured repair), the access case (each module brings its own scaffolding and access plan as part of its invariant), and multi-bot (module-level assignment). Module boundaries also give the decomposition that the cyclic-core idea needs.

**Estimate.** Localizes failures and removes the LLM from the loop for local failures. The trial-count reduction comes from module invariants that the simulator checks once per module rather than once per action. Unverified for Minecraft. The HTN results are on classical domains with a fixed model. Here the invariants must be checked by the simulator, so this composes with v4.1 (it becomes the repair layer) rather than replacing it.

### 4. Multi-bot repair by large neighbourhood search, with independence-based pruning

**Idea.** Plan each bot assuming the others are absent. Detect interference: two actions whose update neighbourhoods overlap, or a bot whose access path is blocked by another's placement. Then repair locally: choose a neighbourhood of interfering bots (or actions), replan only those with the rest fixed, and repeat until the schedule is conflict-free. For the interleaving search itself, use a partial order reduction such as stubborn sets, so the search only branches on orderings of dependent actions.

**Sources.** MAPF-LNS2 (Li et al., AAAI 2022, https://ojs.aaai.org/index.php/AAAI/article/view/21266): starts from colliding paths and repeatedly replans subsets of colliding agents. Per the authors, it is significantly faster than prioritized planning with restarts, EECBS and PPS, near-optimal in most cases, and solves 80% of the largest random-scenario instances in the benchmark suite within 5 minutes. Stubborn sets (Valmari; Wehrle and Helmert, ICAPS 2012, https://ai.dmi.unibas.ch/papers/wehrle-helmert-icaps2012.pdf): expand only a persistent subset of applicable operators; completeness and goal reachability are preserved, and optimal planning is preserved under the paper's conditions. Their relative pruning power against expansion cores is studied in a follow-up paper (ICAPS).

**Mapping.** Attacks the many-bots case. The independence relation for builds is "no shared update neighbourhood and no shared access tile." Builds are spatially spread, so most pairs of bot actions are independent and can be ordered arbitrarily. Repair then touches only the neighbourhoods where bots actually interact.

**Estimate.** Changes the multi-bot cost from global interleaving search to local repair. If builds are spread out, the number of simulator interactions that need checking drops sharply. Unverified for Minecraft. The independence relation must be conservative: block updates propagate over several blocks, and fluids and gravity extend the update radius, so the neighbourhood must include those.

### 5. Undoability and dead-end pre-pass (frozen cells and irreversible states)

**Idea.** For each placement action, check whether it is undoable from the states it is applied in: is there a short reverse sequence (break, re-place, a bot's valid removal with access) that restores the previous state? Actions that are not undoable (memory blocks, one-way latches) are dead-end risks. A partial state is a dead end if some required placement has no reachable access tile, or if a block placed earlier can no longer be removed. The Sokoban freeze-deadlock pattern is the analogy: a block that can never move again makes the goal unreachable.

**Sources.** Faber, Morak and Chrpa (arXiv 2108.05428, https://export.arxiv.org/pdf/2108.05428): deciding universal uniform reversibility via polynomial-length reverse plans is NP-complete, and deciding uniform phi-reversibility is in Sigma_2^P. Simple encodings that check only action preconditions scaled to about 150 facts on artificial domains; general encodings hit time limits much sooner. For Sokoban, the AlphaZero-style paper (arXiv 2006.02689, https://arxiv.org/pdf/2006.02689) notes that specialised solvers depend on handcrafted dead-end detection, and that a learned search solved several hard instances that FF and Sokolution could not.

**Mapping.** Attacks the memory case (irreversible states), the access case (frozen or walled-off cells), and gives a principled version of the owner's static pre-pass that classifies each cell by hazard type. It answers "is this action safe to take now" without a simulator call.

**Estimate.** Gives a cheap rejection test that prunes whole branches before simulation. It does not guarantee correctness, and the full reversibility check is itself hard, so the pre-pass should use the simple per-action version. Unverified for Minecraft. The disassembly idea runs into the same wall: the reverse of a build is not automatically a valid build, because teardown can leave a memory state that differs from the pre-build state. A teardown plan is only usable if the simulator verifies it.

## Further ideas (ranked 6 to 12)

**6. Reduced models with a risky-state predicate (safe-state planning).** Chrpa et al. (AAAI 2020, arXiv 1905.09355, https://arxiv.org/pdf/1905.09355) use a portfolio of reduced models. A predicate D(s') marks risky states. Reachability to risky states is estimated by sampling random walks and solving small problems. The full model is used where risky states are reachable, and a determinised model elsewhere. Reported: 21% to 99.7% time savings, with a cost increase of 0.3% to 17% for the 0/1 reduced model, against up to 88% for most-likely-outcome determinisation. This is the strongest external evidence for the MCHPRS-style fast pre-filter, with a principled way to decide where the fast model may be trusted. Estimate: moderate. The Minecraft outcome set is deterministic, so the reduced model would prune update orders or update sets, not sample outcomes.

**7. Scaffold budget via reversible pebbling.** Model scaffolding as pebbles: a support can be placed only while its own supports exist, and removed only when nothing depends on it. Maximum simultaneous scaffold blocks is the space bound, and placement or removal moves are time. Bennett's reversible pebbling gives time-space tradeoffs. Kornerup, Sadun and Soloveichik (arXiv 2110.08973, https://arxiv.org/pdf/2110.08973v2) give tight bounds for line graphs, show that binary trees need h+1 pebbles, and show that minimising pebbles is PSPACE-hard to approximate for DAGs with maximum in-degree two. Their "spooky" (ghosting) variant allows intermediate garbage as long as it is cleared at the end, which is a loose analogy to temporary wrong states that are later corrected. Estimate: moderate. It gives a lower bound on the scaffold count a given build order needs, but bot reach and line of sight are not pebble rules, so the mapping is analogical. Unverified for Minecraft.

**8. Landmarks (LAMA).** Fact landmarks are states that must hold at some point in every plan; disjunctive landmarks say "one of these facts must hold" (for example, a cell placed from face A or face B). Reasonable orderings are usually respected but not required. The landmark-count heuristic gives a cheap progress estimate. LAMA (Richter and Westphal, JAIR 2010, https://arxiv.org/pdf/1401.3839) combines it with an FF-style heuristic in multi-queue search, and then restarts weighted A* with decreasing weights to improve plans anytime. Mapping: a cheap heuristic for beam or greedy ordering in the static pre-pass, and a way to derive "must place X before Y" constraints. It says nothing about safety, so it should sit in front of the simulator, not replace it. Estimate: cheap ordering; moderate gain.

**9. Learned branching or action priors.** RLAF (Tonshoff and Grohe, ICLR 2026, https://proceedings.iclr.cc/paper_files/paper/2026/hash/a04c50c0bd6937760a3b89ee10010c96-Abstract-Conference.html) trains a GNN with the solver's own runtime as reward, and it outputs per-variable branching weights and polarities in one pass. Reported speedups above 2x on some distributions, with generalisation to larger instances. Mapping: a learned prior over the next placement in the order model, trained on earlier builds' simulator traces. The AlphaZero-style Sokoban curriculum (arXiv 2006.02689) is the planning analogue. Estimate: a prior could cut trials, but training data costs the same simulator time. Low priority until a corpus of traces exists. Unverified for Minecraft.

**10. Staged decomposition with feedback nogoods (Factorio blueprints).** Patterson, Espasa, Chang and Hoffmann (arXiv 2310.01505, https://arxiv.org/html/2310.01505v1) report that a single unified constraint model was infeasible for non-trivial blueprints. They split the problem into recipe selection, then bin-packing, then layout routing, and when a later stage is unsatisfiable the earlier stage produces a new candidate and stores previous attempts to avoid repeats. This is the WorldEdit-style type-staged ordering with backjumping added. The excerpt I read contains no quantitative results. Estimate: the staging is a useful template; the value of the feedback loop is unverified.

**11. Bounded model checking or compositional certification.** Replace statistical certification by timing perturbation with exhaustive checking of small local regions: each redstone module's update neighbourhood is small enough to check all orderings and timings, with assume-guarantee interface assumptions for the boundary. Not searched directly. Unverified; a guarantee-changing idea, and the regions must be small enough.

**12. Anytime and beam methods.** ARA* and beam search are standard tools for getting a complete build quickly and improving it later. Small shape change, but it fits the owner's "stuck report" workflow because a partial build is always available. Not researched in depth.

## Evidence on the ideas already on the table

- **Build cold, arm last.** Supported by feedback arc set theory: arming is exactly the cut of the cycles (idea 2). Against it: the arming set is not free, the arming phase has its own ordering problem, and a minimum arming set is NP-hard. It is a decomposition, not a solution.
- **Static pre-pass by hazard type.** Supported by the reversibility and dead-end work (idea 5). The principled version is undoability per action, not a fixed hazard list.
- **Disassembly planning.** Weak evidence. AND/OR graph disassembly planning with genetic algorithms exists (KAIST, https://koasas.kaist.ac.kr/handle/10203/23645; only the abstract page was seen), but I found nothing on whether a teardown reverses a build safely. Against it as a free lunch: reversal is not guaranteed for memory states. Useful only if the teardown is verified by the simulator.
- **MCHPRS fast pre-filter.** Supported by the reduced-model results (idea 6), with the caveat that the pre-filter must be trusted only where a risky-state predicate says so.
- **WorldEdit type-staged ordering.** Partly supported by the staged-decomposition evidence (idea 10). Its weakness is the lack of feedback from later stages, which is what nogood learning adds.
- **Litematica printers and Baritone.** Not researched; no evidence gathered.

## Consolidated top 5

1. **Simulator as oracle with lazy nogood learning (CEGAR / CBS / lazy clause generation).** It replaces "retry the candidate" with "learn why it failed and never retry that pattern." Failure cores are reusable across repeated modules, and a solver handles the global consistency that a local search cannot. This changes the cost from thousands of simulator trials to one run per failure pattern, provided the cores are small. Its risk is weak nogoods, which the owner's LLM-debugging loop cannot fix, so it is the piece that most needs an experiment.

2. **Strongly connected components plus feedback arc set.** Most of a build is acyclic and can be ordered by topological sort. Search is confined to small cyclic cores, and "arm last" becomes a principled choice of which dependency edges to cut. It attacks the redstone-ordering case directly and makes the search size proportional to the cyclic structure rather than the schematic size. Its success depends on how large the cyclic cores are in real schematics, so the first step is to measure that.

3. **HTN-style module decomposition with causal failure repair.** It gives the owner's stuck reports an automatic, structured repair: find the minimal failed module, freeze the executed prefix, backjump. The published HTN repair work shows no single method dominates and that large problems time out, so it should be a repair layer over v4.1, not a planner replacement. Its main value is that modules become the decomposition unit that idea 2 needs.

4. **Multi-bot repair by large neighbourhood search with independence-based pruning.** Plan each bot alone, then repair only the interacting neighbourhoods, in the manner of MAPF-LNS2. Use a conservative independence relation (stubborn-set style) to skip orderings of independent actions. This turns the many-bots case from a global interleaving search into local repair, and it is probably the largest speedup available when builds are spread out. The update-radius of block physics must be included in the independence check.

5. **Undoability and dead-end pre-pass.** It turns the memory and access cases into cheap rejection rules, checked before any simulator call: an action that cannot be undone from the current state, or a cell that can no longer be reached or removed, is a dead end. It formalises the owner's hazard-class pre-pass and gives a principled test for when a teardown can be trusted. Full reversibility checking is NP-complete in general, so the pre-pass must stay with the simple per-action version.

Next steps if any of these are pursued: measure the cyclic-core sizes of real schematics (idea 2) and the failure-core sizes from a small pilot of idea 1. Those two measurements decide most of the rest.
