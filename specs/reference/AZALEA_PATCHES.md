# Azalea fork patches

**Record, started 2026-10-16.** These are the changes Null made to the Azalea fork at `~/Desktop/null-spikes/azalea`, on top of the 1.21.11 branch and its 38 cherry-picks. Patches 1–15 are committed and pushed to `null-main` (head `586c9b3`, 2026-10-18); Null's `Cargo.toml` pins that head.

**Plan (Allen, 2026-10-16, revised the same day):** upstream asks for no AI-written contributions, so we don't send PRs. We keep our own public fork, [allen546/azalea](https://github.com/allen546/azalea), and expect many more patches. Rules:
- `null-main` (the default branch) is upstream's `1.21.11` + the cherry-picks + the bench timers + our patches, **one commit per patch**, each named `null patch: <n>-<name>`, so a patch can be read, reverted or rebased alone.
- Every patch gets a row in the table below (problem, fix, how it was found) in the same change that adds it.
- Mark each patch as a **bug fix** (upstream could take it) or **Null-only** (behaviour we need and upstream may not want). This tells us what a move to a newer upstream costs.
- Moving to a new Minecraft version means rebasing these commits onto upstream's new branch, so keep patches small and away from generated code.
- **Cite the source (Allen, 2026-10-17; in force from patch 11):** a patch that reproduces vanilla behaviour names the vanilla method in the row, for example "vanilla 1.21.11, Mojang names: `net.minecraft.server.level.ServerPlayerGameMode#handleBlockBreakAction`", and the Grim check it must pass, if any. Read the method in `~/Desktop/null-reference/` (`vanilla-1.21.11-src/` for client and server, `paper/` for Paper, `grimac/`; see its `MANIFEST.md` and [REFERENCE_SOURCES.md](../plans/REFERENCE_SOURCES.md)). Describe the behaviour in our own words; never copy code.

Patches 1-4 were found in the 2026-10-16 swarm duels (`null-node` processes of 8 or 20 bots each, on `skeleton-server`).

| # | file | problem | fix |
|---|---|---|---|
| 1 | `azalea-client/src/plugins/packet/relative_updates.rs` | Bots in one process share a world. Each bot kept its own count of updates per entity, and only a bot whose count matched the shared count could apply the next one. The counts were never synced when a bot loaded an entity. So once the bot that was ahead died, respawned or moved out of range, no bot could update that entity. It froze in place for the whole swarm. Seen as bots chasing enemies' old positions after a teleport, and strafing around "dead bodies". | An `UpdatedBy(Entity)` component names the one bot that applies an entity's updates. When that bot no longer has the entity in its `LoadedBy`, the next bot that gets an update takes over. |
| 1b | `azalea-client/src/plugins/packet/game/mod.rs` (`add_entity`) | When an entity that already exists is re-added (respawn, back in range, teleport), only `LoadedBy` was updated, so its stored position stayed stale. | If no bot that still tracks the entity is driving its updates, take the absolute position from the add packet and make this bot the updater. Never for local (swarm) entities: an early version moved our own bots and piled them up. |
| 2 | `azalea-entity/src/plugin/mod.rs` (`add_dead`) | `Dead` was added at health 0 and never removed. A respawned player keeps its entity id and is re-added onto the same entity, so it stayed `Dead` forever and bots ignored it as a target. | Remove `Dead` from a non-local entity when its health is above 0 again. |
| 3 | `azalea-client/src/plugins/movement.rs`, `lib.rs` | Using an item was a TODO (`using_item = false`). A bot holding up a shield walked and sprinted at full speed, which anticheats flag at once. | A public `ItemInUse` marker, set by whoever sends the use packet. While it is set, input is scaled by 0.2 (vanilla `modifyInput`), sprinting can't start, and an active sprint stops. `mc-adapter` sets it on `UseItem` and clears it on release, offhand swap, slot change and death. |
| 4 | `azalea/src/pathfinder/mod.rs` (`handle_stop_pathfinding_event`) | A stop for a bot with no `ExecutingPath` (its search still running) dropped the search but returned before clearing `goal`, and `is_calculating` stays set until a path arrives. So the bot read "calculating" with nothing running until its next goto. Found 2026-10-16 in the 20 v 20 swarm duel: up to 217 such stops in one match, 5.5 s freezes. | With no `ExecutingPath`, clear `goal`, `opts` and `is_calculating` too. After the fix, three matches had no wait of 2 s or more (before: 7, 0 and 2). |
| 5 | `azalea-client/src/plugins/block_actions.rs` (new), `mining.rs`, `interact/mod.rs`, `client.rs` | Azalea can place and break but never says whether the server accepted it: no placement prediction, the ack sequence is private, and mining has no result. A bot cannot tell a placed block from a refused one, and it could send clicks (out of reach, a face it cannot see, a look that misses) that no vanilla client sends, which Grim flags (`FarPlace`, `PositionPlace`, `RotationPlace`). | New client API, **Null-only** (upstream may want its shape changed). `PlaceBlockQueued { position, direction }` (a component, handled in `GameTick`) and `StopMiningQueued`; `BreakBlockQueued { position }` starts a break in the same tick (the existing `StartMiningBlockEvent` is an `Update` message and lands a tick late). `BlockActionResults { last_place, last_break }` holds `Pending / Accepted / Refused / Cancelled`, judged from the `BlockChangedAck` plus whether the block changed, with tick counts (`finish_ticks`, `ack_ticks`) and a `BlockActionFinished` message. Before sending, the click is checked as a vanilla client would make it: reach to the block, face visible from the eye, crosshair ray on that block and face. If a check fails the action is `Refused` with a `BlockActionRefusal` reason and nothing is sent. Also `BlockStatePredictionHandler::seq()` / `acked_seq()` and a `BlockBreakSent` trigger in `mining.rs` (the sequence number of the finishing packet). Found by the SA ability check (`null-abilitycheck`) and the Grim server. Only breaks started by `BreakBlockQueued` are checked (marker `CheckBreakClick`), so `StartMiningBlockEvent { force: true }` still mines regardless, as its doc says (the fork's `mine_block_*` tests pass). A replaceable clicked block (short grass, water) is the placement target itself, as in vanilla. Commit `145c39d`. |
| 6 | `azalea-client/src/plugins/block_actions.rs`, `interact/pick.rs` | Patch 5's click checks treated every block as the unit cube, so a bot would refuse clicks a vanilla client makes (the top of redstone wire, a chain, a carpet) or aim where the real shape isn't. Azalea's pick ignored interaction shapes (cauldron, hopper, composter, scaffolding), a TODO upstream. Patch 5 judged a missing ack as a refusal and an adventure-mode break as cancelled. | Face visibility tests the eye against each box of the real outline shape; reach stays the unit cube, as the vanilla server and Grim measure it. `LookAtBlockQueued` aims at a visible point of the real shape (with the 0.15° look quantisation) so the crosshair ray lands on that face. `click_replaces` follows vanilla `canBeReplaced` (snow layers, slab merging, the replaceable tag). New refusals `NoAck` and `NotAllowed`. `pick_block` applies the interaction-shape override to the hit face, as vanilla does. **Null-only** (the pick part is a bug fix). Found by the SA shape check (A2S, A4S: 166 rows on Paper + Grim). Commit `ec7f34a`. |
| 7 | `azalea-client/src/plugins/attack.rs` | `TicksSinceLastAttack` was reset after this tick's increment, so the bot's cooldown ran one tick behind the server's, and the tick after an attack still showed the old scale (about 1.0): a skill could swing twice. | Start the counter at 1 and refresh `AttackStrengthScale` in `handle_attack_queued`. A partial-cooldown hit now deals what the bot expects (5.263 at 11 ticks with an iron sword). Sim test `attack_cooldown_like_vanilla`. **Bug fix.** Found by SA A7. Commit `7fa0150`. |

| 10 | `azalea-client/src/plugins/mining.rs`, `block_actions.rs` | Azalea sets `MineDelay = 5` after a finished break but never reads it in survival, and adds progress in the tick a break starts. **How Null builds against the fork (2026-10-17):** `Cargo.toml` pins `azalea` and `azalea-client` to a commit of `allen546/azalea`, so the repo builds on any machine; `.cargo/config.toml` makes the fetch shallow. While editing the fork on this Mac, add to `~/.cargo/config.toml`:

```toml
[patch."https://github.com/allen546/azalea"]
azalea = { path = "/Users/allen/Desktop/null-spikes/azalea/azalea" }
azalea-client = { path = "/Users/allen/Desktop/null-spikes/azalea/azalea-client" }
```

Before committing Null code that needs a new fork patch, push `null-main` and move the pinned `rev` to it.

**Upstream AI policy (read 2026-10-16, `CONTRIBUTING.md`):** "Please avoid using generative AI to make contributions to Azalea. We do not enjoy working with code that wasn't written by people." Hence the fork.

**Packages:** one diff per fix in [azalea-patches/](azalea-patches/), and one branch per fix on the fork, `null/<name>`, each based on the 1.21.11 head and compiling alone. Patches 1–4 are bug fixes; 3 also adds a public marker. Patches 5–15 have diffs here but no per-fix branches: they depend on each other (6 on 5, 8 on 3, 10 on 5), and the branches existed only for upstream PRs. Upstream `main` still had bug 4 on 2026-10-16.

If upstream ever wants one of the bug fixes, check first:
- Check whether upstream has fixed any of these since.
- Add tests in Azalea's style for 1 and 2 (two simulated clients sharing an entity, the updater leaves; a player dies and respawns).
- For 3, upstream will probably want Azalea to track item use itself instead of a marker.
