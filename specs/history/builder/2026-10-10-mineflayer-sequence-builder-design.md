# Mineflayer Sequence Builder Bridge Design

## Overview
This document specifies the design for bridging an established Mineflayer builder into the build sequence generated by the planner (`planner/out/plan.json`). The builder executes the planned block placements on a live Minecraft server with server ticks **running normally (never frozen)**, using prototype cheats (creative flight, peaceful, invincible player) while strictly adhering to **survival placement semantics** (no `block_state` NBT components on items, proper player aiming, click adjustments, and temporary scaffolding).

Importantly, the planner's proof was established **for plugin placement** (`PlanSim.opPlace` under tick sprints with `quiet=20` settle detection). This document identifies every point where physical bot execution diverges from that proof, introduces an offline **Pre-Flight Pass** to detect physical bottlenecks and generate re-provable scaffold steps, and defines the exact executor mechanics.

---

## Where Bot Execution Leaves the Proof

The planner proved `plan.json` under specific conditions in `plansim-plugin`: `opPlace` set the block directly via `level.setBlock(..., UPDATE_ALL_IMMEDIATE)` and `setPlacedBy`, applying `keep_props` in a single atomic call, and checked quiet settle windows via server-side tick queues. Real bot execution diverges from this in five fundamental ways:

| Divergence | Plugin Proof Behavior | Bot Execution Reality | Gap & Handling |
|---|---|---|---|
| **1. Scaffolds** | Placed blocks directly in mid-air (`setBlock`) without support blocks. | Survival placement requires clicking an existing adjacent block face. Mid-air blocks require a temporary scaffold block. | Every scaffold placement and removal is an unproven state change that can trigger observers or bud pistons. **Handled by Pre-Flight Pass**, which emits explicit scaffold steps that can be re-proven in the simulator. |
| **2. Multi-Action States** | Set multi-state blocks (e.g. `repeater[delay=3]`, `comparator[mode=subtract]`) in a single atomic write. | Freshly placed repeaters start at `delay=1`. Bot must click twice to reach `delay=3`. | Intermediate states (delay 1, delay 2) exist on a live un-frozen server and can pulse or propagate before reaching target state. |
| **3. Timing & Settle** | Strict settle rule: `quiet=20` consecutive game ticks with 0 pending block ticks, 0 fluid ticks, 0 block events, 0 moving pistons, and 0 entity movements. | Real bot movement is variable and slower. A fixed delay (e.g. 50ms) does not mirror the settle rule. | Executor connects to the plansim plugin's `status` TCP port (`127.0.0.1:25580`) or polls world state to mirror the exact `quiet=20` settle rule between active sections. |
| **4. Accessibility** | Placed blocks into completely enclosed 1x1 cavities without physical line-of-sight. | Bot needs: stand position ($r \le 4.5$), collision-free line of sight, clickable target face, and bot bounding box not intersecting the target cell. | A valid topological order may be physically obstructed. Pre-flight pass detects enclosed/unreachable cells early. |
| **5. Update Semantics** | Plugin used `UPDATE_ALL_IMMEDIATE` and `setPlacedBy`, but started with `keep_props` applied before neighbour shapes. | Player placement calls `getStateForPlacement` (which derives facing from player yaw/pitch and clicked face). | Placement angles must be precisely calculated to land in the correct initial state. |

## Pre-Flight Pass

Before connecting to or modifying the live world, an offline pre-flight simulation analyzes `plan.json` against a 3D voxel grid initialized to the starting world state:

```
                  ┌──────────────────────┐
                  │      plan.json       │
                  └──────────┬───────────┘
                             │
                             ▼
                  ┌──────────────────────┐
                  │   Pre-Flight Pass    │
                  │ (Voxel Grid Tracker) │
                  └──────────┬───────────┘
                             │
         ┌───────────────────┴───────────────────┐
         ▼                                       ▼
┌──────────────────┐                   ┌──────────────────┐
│  Early Failure   │                   │  Augmented Plan  │
│ (Unreachable /   │                   │ (plan_augmented  │
│  Sealed cavity)  │                   │  with scaffolds) │
└──────────────────┘                   └─────────┬────────┘
                                                 │
                                                 ▼
                                       ┌──────────────────┐
                                       │ Simulator Proof  │
                                       │ (re-verify in    │
                                       │  planner/sim.py) │
                                       └──────────────────┘
```

### Classification per Step
For each step in `plan.json`:
1. **`direct`**:
   - An adjacent solid face exists within reach.
   - At least one collision-free standing position exists within $4.5$ blocks.
   - Direct placement with survival aim vector produces the required base state.
2. **`adjusted`**:
   - Direct placement is possible, but requires $N$ post-placement right-click interactions (e.g. repeater delay, comparator mode, note block pitch).
3. **`scaffold`**:
   - Target position has no existing adjacent solid face.
   - Evaluates neighbor positions $(x \pm 1, y, z)$ or $(x, y - 1, z)$ for anchor support.
   - Determines the exact scaffold coordinate and placement face.
   - Emits explicit synthetic steps:
     - `{"op": "place", "pos": scaffold_pos, "state": "minecraft:dirt", "scaffold": true}`
     - Original `place` step (placing against the scaffold face)
     - `{"op": "remove", "pos": scaffold_pos, "scaffold": true}`
4. **`unachievable`**:
   - Block is inside a sealed cavity with no line-of-sight from any valid standing position.
   - Halts immediately with a detailed diagnostic report before touching the live server, allowing the sequence generator to re-order or insert access holes.

### Re-provable Scaffolds
The pre-flight pass outputs `plan_augmented.json`. Because scaffold placements and removals are explicit steps, this augmented plan can be run through `planner/execute.py` against `plansim-plugin` to verify that temporary scaffolds never trigger redstone or cause irreversible events!

## Detailed Executor Mechanics

### 1. Item Provisioning (No `block_state` NBT)
- Uses `bot.creative.setInventorySlot(slot, item)` with pure vanilla item definitions.
- Items are strictly clean instances: `new Item(itemId, count)` with **no `components`** or custom block state NBT.
- Fluids: `water_bucket` for water sources, `lava_bucket` for lava sources.
- Tools: `diamond_pickaxe` / `diamond_shovel` for digging removal steps or scaffolds.

### 2. Aiming and Orientation Math
- **Directional Blocks (Pistons, Observers, Droppers, Dispensers)**:
  - **Pistons / Droppers / Dispensers**: In vanilla survival, placing a piston sets its facing **toward the player's eye direction** (the piston head extends toward the player). To achieve `facing=north`, the bot must be positioned on the north side looking south.
  - **Observers**: In vanilla survival, placing an observer sets its redstone output face **toward the player** and its sensor face **away from the player**. To achieve `facing=north` (sensor pointing north), the bot must be positioned on the south side looking north.
- **Horizontal Directional (Repeaters, Comparators, Stairs)**:
  - Controlled by player horizontal yaw at placement time.
- **Half / Slabs / Trapdoors**:
  - Sub-block click coordinate determines `half`:
    - Top slab / top trapdoor: hit vector $y \ge 0.5$ on reference face.
    - Bottom slab / bottom trapdoor: hit vector $y < 0.5$ on reference face.
- **Raycast & Sneaking Rules**:
  - **During Placement (`placement.js`)**: Bot enables sneaking (`setControlState('sneak', true)`) to prevent accidentally opening containers, trapdoors, or interacting with existing blocks.
  - **During Adjustment (`adjust.js`)**: Bot **must disable sneaking** (`setControlState('sneak', false)`), because sneaking prevents right-click block state interactions on repeaters and comparators!

### 3. Click Interactions (`adjust.js`)
- `adjust.js` strictly realizes target states specified by the plan's `place` step:
  - **Repeater**: If target specifies `delay=N` ($N \in \{2, 3, 4\}$), bot sends $(N - 1)$ right-clicks.
  - **Comparator**: If target specifies `mode=subtract`, bot sends 1 right-click.
  - **Note Block**: Right-clicks until tuned note matches target.
- `adjust.js` **never** toggles arbitrary redstone components on its own; all `use` operations (such as flipping a control lever) are owned strictly by explicit plan steps.

### 4. Settle Detection on Un-Frozen Server (`settle.js`)
- Because the server is live, the executor connects to the simulator plugin's status endpoint (`127.0.0.1:25580`) via TCP:
  - Calls `status` for the bounding region.
  - Verifies: `blockTicks == 0`, `fluidTicks == 0`, `blockEvents == 0`, `movingPistons == 0`.
  - Maintains a `quiet` counter: requires $20$ consecutive quiet game ticks (1.0 second of silence) before completing active sections.
  - Falls back to client-side entity/block update quiet window if status endpoint is offline.

### 5. Section Boundary Checkpoints (`checkpoint.js`)
- At the end of each section:
  - Queries world block states in the section's bounding box.
  - Compares against target states using the exact property classes from `planner/checkpoint.py`:
    - Placement-determined & derived properties must match.
    - Cosmetic connection shape (dust dot vs cross, straight rail shape) is ignored at intermediate checkpoints.
    - If mismatch or unintended regression occurs: halts immediately, records failing section and diff.

### 6. Resume & Idempotency
- Each step is idempotent:
  - Before flying or placing, checks `bot.blockAt(worldPos)`.
  - If the block already matches the target state, the step is recorded as satisfied and skipped.
  - Supports `--resume <section_id>` to continue interrupted builds seamlessly.

## Error Handling & Recovery
1. **Physical Retries**:
   - Up to 3 placement attempts per step.
   - If line-of-sight is obstructed or player is in the placement box:
     - Steps back $1.5$ blocks along the face normal.
     - Clears velocity, re-aims, re-sends placement packet.
2. **Scaffold Integrity**:
   - Scaffold blocks are placed only at coordinates vetted by the pre-flight pass.
   - Scaffolds are tracked in an active set; must be cleaned up before section boundary check.
3. **Deterministic Abort**:
   - On unrecoverable error (e.g. 3 failed attempts or checkpoint mismatch), stops bot movement, outputs `failure_report.json` with step index, coordinates, expected vs observed state, and logs.
